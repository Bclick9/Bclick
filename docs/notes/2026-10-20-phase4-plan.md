## 1. Purpose and boundaries

Implement player and administrator identity/session foundations locally while preserving the existing storefront and Backoffice UI. Build from the existing Phase 3 Fastify skeleton in `server/`; do not rename the `backend/` workspace, which is the Backoffice/CMS React application.

This is a local-development phase only. The Project Owner's Q-011 controlled exception permits Phase 4 development to proceed while staging/backup work runs in parallel. Q-011 remains P0/Open and continues to block any real deployment and any provider integration/callback, wallet, payment or real-money route until the actual restore drill passes.

### In scope

- Player registration, login, logout, session lookup/revocation, email verification and password-reset request/confirmation according to the current OpenAPI contract.
- Separate player and admin principals and session namespaces; opaque random session tokens with only token hashes persisted.
- Admin password challenge, TOTP enrollment/verification, MFA-required login, one-time recovery codes and protected MFA reset workflow.
- Server-derived roles/effective permissions, per-handler RBAC checks and audit events for authentication/security actions.
- Signed, session-bound double-submit CSRF, strict exact-Origin allowlists and browser-tested cookie behavior.
- Local-only bootstrap and email-testing path with no default/committed credentials and no external side effects.
- Route-level runtime contract tests in CI as each real handler is added.

### Out of scope (must stay disabled)

- Wallet/ledger tables or movements, deposits, withdrawals, balance changes, payment rails or financial administration.
- TND/currency routing or provider-specific currency behavior; no currency/precision implementation beyond preserving the existing registration contract fields.
- Aggregator, BigBang, WinHouse or any provider integration, launch, callback, sandbox or production credential.
- CMS media upload/publish, casino catalogue migration, sportsbook mutations, production/VPS deployment or real-money behavior.
- Closing Q-020 or Q-011 based on documentation, fixtures or a runbook alone.

## 2. Read-back of the accepted decisions

The Project Owner approved Q-001, Q-002 and the Q-003 CSRF policy on 2026-10-20. The approvals are recorded in the shared Library source `docs/planning/12-open-questions.md` and in Issue #55. They do not make unimplemented routes operational, and the Phase 4 contract/test preparation step must be green before handler implementation.

### Q-001 — Canonical admin session

Target response shape:

- `data.admin`: `id`, `email`, `displayName`, `status`.
- `data.roles[]` and effective `data.permissions[]`, derived from current server-side RBAC.
- `data.mfa`: `enabled`, `method`.
- `data.session`: `authenticatedAt`, `expiresAt`.

Required semantics:

- `200` only for an active admin with a valid full server-side session and completed mandatory MFA; successful response has `mfa.enabled=true` and `mfa.method=totp`.
- `401` for missing, malformed, expired, revoked or MFA-incomplete authentication.
- `403` for a known locked/disabled or otherwise barred admin, using the standard safe error envelope and no successful session payload.
- No password, session token, TOTP seed, recovery code or other credential is returned.
- Client permission data is presentation-only. Every protected server handler independently checks its required permission.

**Contract mismatch to fix before code:** the current repository OpenAPI allows locked/disabled status in the successful AdminSessionResponse, allows MFA disabled/null, and does not require displayName. The contract-preparation change must make the schema agree with the accepted semantics and verify the session timestamp fields exactly.

### Q-002 — MFA, enrollment, recovery and reset

The login password step returns only a short-lived server-side challenge (HTTP 202); it never grants a full admin session. Challenge lifetime is at most five minutes with bounded attempts and one-time consumption. The response must distinguish `mfa_required` and `enrollment_required`. Emit the short-lived HttpOnly enrollment cookie and enrollment-bound CSRF material only in the enrollment case, and restrict that cookie to the TOTP enrollment routes.

Before implementation, make the challenge-to-browser binding normative: the challenge ID is a locator, not a bearer authorization secret. Recommended design is server-side one-time challenge state bound to admin principal, environment, expiry, attempt counter and a random short-lived browser challenge cookie (stored by hash); the enrollment cookie remains a separate restricted credential. This binding must be written into OpenAPI prose/fixtures and tested for replay and cross-browser reuse.

- A full session is issued only after valid TOTP or one-time recovery-code redemption.
- Store TOTP seeds encrypted at rest; never log the seed/QR payload or return an existing seed after enrollment.
- Show recovery codes once, store salted hashes (with server-held pepper), redeem atomically once, rate-limit attempts, and revoke old codes on regeneration.
- First admin is provisioned through a documented one-time out-of-band bootstrap; no public admin self-registration and no fixed/committed `admin/admin` password. The intended initial username may be `admin`.
- MFA reset requires a ticket/reason, audit trail, revocation of affected sessions/factors and `requester != approver != target`. The API must reject self-approval. Since the initial deployment has only one admin, the ordinary three-principal reset cannot complete in that topology; use the separately documented out-of-band break-glass/bootstrap process until independent principals exist. Never weaken the separation rule to make the UI appear functional.

### Q-003 — CSRF and Origin

Accepted policy: signed session-bound double-submit CSRF, a JavaScript-readable CSRF cookie and exact matching `X-CSRF-Token` header, plus a strict per-environment exact-Origin allowlist. Bind tokens to the active session ID/version, or the restricted enrollment challenge; compare safely after length/format checks; never log tokens. Rotate on login, MFA completion, session rotation/privilege changes, logout and revocation. Check Origin and apply abuse limits to unauthenticated login/register/reset too; those routes do not require an authenticated CSRF token. SameSite is defense-in-depth, not the CSRF control. Provider callbacks are out of scope.

**Accepted CSRF separation amendment (2026-10-20):** use three separate host-only names in both development and production: `__Host-bclick_player_csrf`, `__Host-bclick_admin_csrf`, and `__Host-bclick_admin_enrollment_csrf`. This is required on shared-host `localhost` because cookies are not isolated by port, and it avoids relying on a production admin-subdomain assumption. See [the CSRF amendment note](./2026-10-20-phase4-csrf-update.md). The cookie name is selected explicitly by security context; no endpoint may fall back to another context's token. 

Each CSRF cookie uses `Secure; SameSite=Strict; Path=/; no Domain; not HttpOnly`. The `__Host-` prefix requires `Secure`, `Path=/`, and no `Domain`. The player cookie is issued with successful player session establishment, rotated on player session rotation/privilege change, and cleared on player logout/revocation. Admin CSRF is issued only after successful admin MFA verification creates a full admin session, rotated on admin session rotation/privilege change, and cleared on admin logout/revocation. Enrollment CSRF is emitted only for `enrollment_required`, bound to the short-lived enrollment challenge, and deleted on expiry/revocation or successful TOTP verification, when full admin session and fresh admin CSRF are issued. Exact production hostname/path topology remains a pre-deployment decision; do not assume subdomain separation. Browser cookie tests must use secure local HTTPS, not weaker plain-HTTP cookie settings.

Because `__Host-` cookies require secure-cookie behavior, browser tests must use a verified secure local origin (preferred: trusted local HTTPS/reverse proxy) or explicitly prove the supported local browser behavior. Never remove Secure or loosen production cookie rules just to make HTTP development pass. Configure exact allowed origins per environment; no wildcard.

## 5. Required tests and acceptance criteria

### Admin session (Q-001)

- Active admin + full session + verified TOTP returns 200 with every accepted field and no credential/session secret.
- Missing, malformed, expired, revoked or challenge-only session returns 401.
- Locked/disabled/otherwise barred admin returns 403 with the standard error envelope, not a successful session body.
- `displayName`, MFA state and timestamps match the approved schema; unknown status fails closed.
- Effective roles/permissions come from the database/current server state; permission revocation takes effect and every protected handler checks permission independently.

### MFA and recovery (Q-002)

- Password success alone never creates a full session; only a valid TOTP or one-time recovery code does.
- Distinct fixtures prove the `mfa_required` versus `enrollment_required` response, and the enrollment cookie/CSRF material is emitted only for enrollment.
- Challenge is limited to at most five minutes, principal/environment/browser context bound, attempt-limited, consumed once and rejects replay/cross-browser use.
- TOTP enrollment secret is displayed once, encrypted at rest and never logged; invalid, expired and replayed codes fail closed.
- Recovery codes are displayed once, stored only as salted hashes with pepper, rate limited, and one-time redemption is atomic; regeneration invalidates prior codes.
- MFA reset enforces requester, approver and target as three distinct principals, ticket/reason, audit, session invalidation and no self-approval; the single-admin break-glass path is operationally documented and does not bypass API approval rules.

### CSRF, Origin and browser cookies (Q-003)

- Valid same-origin unsafe request succeeds; absent/untrusted Origin, missing token, missing cookie, header/cookie mismatch, bad signature, expired token, wrong session/version, malformed or duplicate cookie fails closed.
- Token rotation/clearing occurs on login, MFA completion, session rotation, privilege change, logout and revocation.
- Player, admin and enrollment tokens cannot overwrite or be confused with one another; enrollment cookie cannot read Backoffice data or access unrelated mutations.
- Cookie attributes are validated in a real browser: Secure, Path=/, no Domain, expected SameSite, JS-readable CSRF cookie and HttpOnly session/enrollment cookies as appropriate. Test on secure local origin; do not infer browser cookie behavior solely from Fastify injection.
- Login/register/reset do not require an authenticated CSRF token but enforce exact Origin and abuse/rate controls.

### Player identity and generic runtime contracts

- Registration validates contract-required fields and normalization/uniqueness; login errors do not enable account enumeration.
- Sessions rotate/revoke correctly; reset and verification tokens expire and are consumed once; password reset revokes existing sessions as specified.
- Passwords use Argon2id; logs, responses and audit metadata never contain passwords, one-time tokens, TOTP seeds, recovery codes or session tokens.
- Applicable 400/401/403/409/422/429 results use the documented envelope and request ID.
- CI runs the static contract checks plus runtime tests for every implemented handler. Q-020 remains open until all relevant implemented operations and later approved provider callback routes are covered at runtime.

## 6. Risks and mitigations

| Risk | Mitigation / gate |
|---|---|
| One CSRF cookie name for three independently bound contexts | Resolve before code: separate names (recommended) or testably separate hosts. No shared-name implementation on same-host localhost. |
| `__Host-` Secure cookie behavior differs on plain local HTTP | Use trusted local HTTPS for browser tests; never drop Secure to make dev easier. |
| Initial single admin cannot satisfy a three-principal MFA reset | One-time, audited out-of-band bootstrap/break-glass procedure; API must still deny self-approval. |
| First-admin bootstrap secret or recovery material leaks | No fixed/default/committed secret; one-time delivery/consumption; keep secrets out of source, image layers, browser bundle and logs. |
| Auth challenge or reset token replay | Store only token hashes where applicable; expiry, bounded attempts, atomic one-time consumption, principal/environment binding and replay tests. |
| Session permissions become stale or are trusted from UI | Server-derived RBAC on each protected handler; tests cover revocation and insufficient permission. |
| Rate limits are only process-local and vanish on restart | Make account/challenge attempt controls persistent and transaction-safe; document any local-only IP limiter; Q-014/staging abuse-tuning stays open before beta. |
| Local/test email accidentally reaches real people | Local-only mail sink and explicit environment fence; production email delivery remains disabled. |
| Phase 4 inadvertently enables financial/provider behavior | Review the route inventory and diff; no wallet/provider routes or secrets; feature-specific launch gates remain closed. |
| Q-011 exception is interpreted as permission to deploy | State remains P0/Open; local development only. Deployment/provider/real-money path is blocked until measured restore evidence is accepted. |
