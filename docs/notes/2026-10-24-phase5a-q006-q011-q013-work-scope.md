# Phase 5A and independent gate execution scope

**Recorded:** 2026-10-24  
**Release boundary:** no live provider callback, wager, deposit/withdrawal, payment, FX, wallet posting, Premium activation or real-money route is authorized by this work.

## Phase 5A — wallet/ledger service acceptance

Track the bounded PostgreSQL-backed implementation and test scope in [Issue #157](https://github.com/Bclick9/Bclick/issues/157). Reuse the current schema from Migration 006 and precision contract from Migration 008; do not recreate wallet tables or rewrite the TND decision. Existing wallet tests include direct SQL rehearsal, so the new acceptance must drive the actual posting/application service against disposable PostgreSQL and prove idempotency/conflict behavior, concurrent no-overdraft debits, reserve/release/settle/reverse semantics, per-currency journal balance, account_balances projection agreement, full transaction rollback, and absence of external calls inside the DB transaction.

## Q-006 — provider evidence

Track BigBang and WinHouse callback/authentication/retry/idempotency/reconciliation questions in [Issue #158](https://github.com/Bclick9/Bclick/issues/158). Maintain a dated evidence register with the official recipient/support channel, send evidence/ticket, document version and SHA-256, and provider response. A drafted message or local fixture is not proof of sending or vendor acceptance. Preserve the confirmed TND 2dp contract.

## Q-011 — restore drill

[Issue #57](https://github.com/Bclick9/Bclick/issues/57) remains open. The wallet/ledger schema is present; no backup/restore readiness may be claimed until an isolated staging restore from an actual base backup plus WAL is timed and evidenced. After restoring, inspect real database state, validate migration version, reconcile per-currency journals and account_balances using retained test evidence, and measure RPO ≤15 minutes / RTO ≤8 hours. Keep provider callbacks and external side effects disabled.

## Q-013 — actual CSP and Host-header verification

Track the deployed-header and trusted-host audit in [Issue #159](https://github.com/Bclick9/Bclick/issues/159). Bclick uses the WinHouse embed.js flow, so verify script-src for the loader and frame-src only for frames actually loaded. Separately verify frame-ancestors (who may frame Bclick), exact effective response headers, and rejection of untrusted Host/X-Forwarded-Host/Forwarded inputs. Adding a header line or seeing a local render is not acceptance.

## PR #151 — operator safety barrier

[PR #151](https://github.com/Bclick9/Bclick/pull/151) stays open and unmerged while the break-glass tool receives an off-by-default feature flag and an unconditional production-environment refusal, followed by CI and an independent security review. Passing CI does not authorize operational use; identity, deployment, and Q-011 gates remain separate.
