# Server database migrations

Schema changes are explicit, ordered, reviewed and run with `node-pg-migrate`:

```powershell
$env:DATABASE_URL = 'postgresql://bclick_dev:local_only_change_me@127.0.0.1:5432/bclick'
pnpm --filter @bclick/server migrate:up
```

The identity schema is managed by the ordered SQL migrations in this directory. Migration 004 adds a separate sequence-backed public player number and editable personal-profile columns to the existing `players` table. The UUID `players.id` remains the internal primary key and foreign-key target; UI/support-facing player IDs use `player_number`. Username is required for new registrations and can be used for login. Existing accounts may continue to log in by email and can set a username once in Personal Info; usernames are case-insensitive and immutable after set.

The first public player number is `100000000` (nine digits). IDs increase by one without wrapping; after `999999999`, the next ID is `1000000000` (ten digits). Existing players are assigned numbers deterministically in creation order during Migration 004. Migration 005 reconciles local databases that already applied the earlier Migration 004 starting at `436222976`: when that known legacy starting number is still present, it accepts gaps caused by deleted local/test accounts if all numbers remain unique and are covered by the sequence high-water mark, then rebases surviving accounts in their existing number order starting at `100000000`. If the known legacy start is missing, it refuses to guess. IDs already in the approved namespace are never renumbered; their sequence high-water mark is preserved to avoid reusing deleted IDs. Unexpected states are rejected. Fresh databases are left at the approved start. Migration 005 intentionally blocks rollback to avoid silently changing IDs already shown to players.

Migration 004 also reconciles the existing Migration 003 profile and credential compatibility mirrors for accounts that were created after Migration 003. The active identity service still treats `players` as the source of truth. Keep those mirrors synchronized until a separately reviewed read/write cutover is approved.

Do not run local development migrations against Neon or another shared/prod database. Review the target connection carefully and test schema changes against a disposable database before approving them. Do not enable automatic schema sync at server startup. Rollbacks must fail closed rather than silently dropping public player identifiers or saved personal profile information.

Migration 006 adds the Phase 5 wallet ledger foundation: `wallet_accounts`, `account_balances`, `journal_transactions`, and `ledger_entries`. It verifies the exact seven-migration pre-state and the existing TND=3, EUR=2, USD=2 currency registry. It provisions zero-balance available/held accounts for existing players, and registration provisions the same accounts for new players. Empty provisioning is not a deposit or opening credit.

Every committed journal is checked at deferred constraint time: at least two entries and a zero sum for every currency. Journal and entry rows are append-only; entries must be inserted in the same database transaction as their journal, and their currency must match their account. The validation serializes on touched wallet-account rows, checks player available/held balances against the authoritative ledger, rejects overdrafts, and updates `account_balances` within the posting transaction. The projection can be reconciled to or rebuilt from the ledger; it is never the financial source of truth.

The disposable PostgreSQL rehearsal for Phase 5 is `server/test/wallet.test.ts` and the dedicated GitHub workflow is `.github/workflows/wallet-migration-006-rehearsal.yml`. It checks balanced/unbalanced journals, late append, immutability, cross-currency rejection, overdraft/concurrent debit behavior and the authenticated read endpoints. Migration 006 rollback intentionally fails closed; do not manually delete migration history or financial rows. No deposit, withdrawal, provider callback or real-money route is activated by this migration.

## Catalogue and currency migrations (007–010)

Migration 007 creates the local BigBang catalogue tables for providers, canonical games, source records, canonical categories, and sync-run history. Bclick UUIDs are the internal game identities; provider identifiers are source-mapping keys and public slugs are unique, stable lookup strings. The current adapter is Standard-Sandbox-only. The schema and browse endpoints do not enable real-money mode, provider wallet callbacks, or wallet posting. Its rollback refuses while any catalogue state exists.

Migration 008 aligns TND database precision with the accepted provider contract: `0.01 TND = 10 millimes`, with two fractional decimal places. It changes the registry from three decimal places to two only when there are no TND ledger entries and every projected TND balance is zero. It must fail closed when either precondition is not met. The migration has not been run against Neon/Production; keep the application-code and database-schema versions aligned, and verify the target on an approved non-production environment before any separately authorized execution.

Migration 009 creates `casino_game_legacy_slug_aliases`, a persistent mapping for the 59 curated game slugs in `frontend/data/catalog.ts`. Aliases start unresolved. A completed, validated Standard Sandbox sync resolves an alias only when exactly one available BigBang game matches both its stored legacy title and provider (case-insensitive and ignoring surrounding whitespace). Once resolved, the alias stays pinned to the canonical Bclick UUID; title-only/fuzzy matching is not used. Unmatched legacy aliases return a safe 404, and ambiguous aliases return 409 rather than guessing. Migration 009's rollback refuses while any alias seed exists because those slugs are persisted public routes.

The disposable PostgreSQL catalogue integration test in `server/test/bigbang.test.ts` applies the ordered migrations through 009 and exercises the alias sync and legacy lookup. This CI rehearsal is not evidence that any migration was applied to a shared, staging, or production database. Do not manually remove migration history, alias seeds, or catalogue records to force a rollback.


Migration 010 makes BigBang source identity tier-aware before any future Premium import: source rows are uniquely identified by `(source_code, source_mode, external_game_id)`, and each canonical game can have at most one source row per provider and tier. It also requires `is_premium` to agree with `source_mode`. The migration does not fetch or import Premium games and does not authorize a live key. Standard-only catalogue routes, the current Sandbox client and demo-launch lookup explicitly filter to `source_mode='standard'`. Rollback refuses if Standard/Premium rows collide under the former tier-blind keys; do not force rollback after importing tier-distinct sources.

Migration 011 adds Bclick-owned provider and canonical-game availability switches with per-change actor/time fields, an integration settings row locked to Standard, and the `casino.provider-settings.manage` permission for the existing `project-admin` role. Admin control mutations update the setting and `audit_events` in the same SQL statement. Public Standard Sandbox catalogue/category/provider/detail/legacy-alias reads and demo launch must fail closed when either Bclick switch is off. The API only reports Standard as supported; Premium remains unavailable and no tier switch, live key, real Play route, wallet callback or money movement is enabled. Migration 011 is deliberately forward-only so a rollback cannot silently erase operator controls.
